## 1. What Worked

**The CommandLine field contained the full attack in one event.**
Sysmon Event ID 1 captured the complete PowerShell command including the task name, payload path, trigger interval, run level, and user context. A single event provided everything needed to confirm the attack, assess the risk level, and make a triage decision. No correlation across multiple events was required to reach a conclusion.

**Layered detection across two event types added resilience.**
Event ID 1 caught the process creating the task. Event ID 11 caught the XML file being written to System32\Tasks. Either alone is sufficient to detect the attack. Together they provide two independent confirmation points from different log sources — if one source had a collection gap, the other would still fire.

**Payload path analysis was definitive.**
`C:\Windows\Temp\payload.exe` is not a path any legitimate software uses to register a scheduled task. The moment the payload path appeared in the command line, the triage decision was made without ambiguity. No further investigation was needed to classify this as a true positive.

**The disguised task name did not evade detection.**
"MicrosoftEdgeUpdateTaskCore" was chosen to look legitimate. The detection rule does not care about the task name — it monitors the behaviour (PowerShell registering a task with a suspicious payload path). An attacker can name a task anything they want and the rule still fires.

**Detection was pre-execution.**
The task was caught within 3 minutes of registration, before the 5-minute trigger interval had elapsed. No payload execution occurred. Catching a persistence mechanism before it fires is the best possible detection outcome.

## 2. What Needed Tuning

**The initial broad query returned noise from legitimate software.**
The first version of the PowerShell rule matched any use of Register-ScheduledTask without filtering on payload path or privilege level. Software deployment tools and legitimate applications that use PowerShell for task management triggered false positives. Adding payload path risk scoring and excluding known-good parent processes reduced noise significantly.

**schtasks.exe coverage was added after the initial rule.**
The primary rule only covered PowerShell-based task registration. Attackers also use `schtasks.exe /create` from cmd.exe — a method that produces different Sysmon event characteristics and would not have matched the original rule. Adding a secondary rule for schtasks.exe closed this gap.

**No automatic parent process chain investigation.**
The alert surfaced powershell.exe as the Image and cmd.exe as the ParentImage. In a real attack, the parent process chain often goes further — a malicious document spawning cmd.exe spawning PowerShell. Building automated parent process chain queries into the investigation workflow would surface the initial access vector faster.

## 3. What I Would Do Differently

**Add a task name allowlist from day one.**
In a production environment, the set of legitimate scheduled tasks is known and relatively stable. Comparing every new task registration against an approved list would catch malicious tasks even when the attacker uses a trusted binary path as the payload. This approach is more comprehensive than payload path filtering alone.

**Include Windows Event ID 4698 as a third detection layer.**
Windows Security log Event ID 4698 (A scheduled task was created) is generated by the Windows audit subsystem independently of Sysmon. Adding this as a third log source would provide detection coverage even in environments where Sysmon is not deployed, and corroborate Sysmon findings when it is.

**Test with more evasive task creation methods.**
This simulation used the PowerShell Register-ScheduledTask cmdlet — a visible and commonly detected method. Real attackers use COM objects to interact with the Task Scheduler API directly, bypassing PowerShell and schtasks.exe entirely. Testing this method would validate whether the Event ID 11 tertiary rule alone is sufficient to catch the most evasive approach.

**Correlate with network events to assess payload activity.**
If the payload had executed before detection, the next visible signal would be a network connection from payload.exe. Integrating network flow log correlation into the investigation runbook would allow the analyst to immediately assess whether the payload had called out to a command-and-control server, changing the incident scope from persistence to active compromise.

## 4. Key Takeaways for SOC Work

**Scheduled tasks are more dangerous than registry run keys for one reason: they do not need a user to log in.** A registry run key sits dormant until the user logs in. A scheduled task fires on a timer regardless of user activity. An attacker who plants a scheduled task and is disconnected from the network will still receive a callback from the payload at the next trigger interval — no further user action required.

**The CommandLine field is the most important field in scheduled task investigations.** It contains the task name, payload, trigger, and privilege level in a single string. Analysts who learn to parse command lines quickly will triage these alerts faster than those who rely only on the Image field.

**Task names are cheap to disguise, payload paths are not.** An attacker can name a task anything. They cannot easily install a payload in Program Files without administrator access, and dropping payloads in trusted system locations risks overwriting legitimate files or triggering other detections. The payload path is therefore the highest-fidelity indicator — more durable than task name, more specific than process name alone.

**Three detection rules for one technique is appropriate, not excessive.** Each rule covers a different attack method. Relying on a single detection for a technique with multiple execution paths creates blind spots. In a production SOC, detection engineering for well-known persistence techniques should cover every documented execution method, not just the most common one.
